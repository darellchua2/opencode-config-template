# OpenCode Configuration

User-level instructions injected into every opencode session (primary + inherited subagents). Terse by design: opencode's own agent picker, `description` frontmatter, and `available_skills` listing already surface *which* agents/skills exist and their triggers — this file encodes only rules the model would get wrong without them.

## Task Delegation Order

1. **Subagents first** — delegate to the specialized subagent whose `description` matches the task (opencode lists them); use the Task tool. Fall back to built-in `general` for multi-step/parallel work and built-in `explore` for read-only codebase search.
2. **Skills second** — load via the Skill tool only when no subagent fits.
3. **Direct last** — trivial tasks or explicit user request only.

**Skill vs subagent decision:** load a skill directly when you need *knowledge/procedure* to apply in your own context (commit formatting, a decision tree, a checklist); spawn a subagent when the *work itself* would flood your context (reading many files, long tool-call chains) or needs a fresh window + specialized permissions. Rule of thumb — **skill = knowledge you lack; subagent = context you want to protect.**

**Non-obvious routing exceptions** (the model would default wrong without these):
- OpenAPI contract review / breaking-change detection: **no subagent** — load `openapi-contract-adherence-skill` directly when trigger phrases appear ("openapi diff", "api contract", "breaking change", "consumer update plan", "spec changed"). Reactive only — use after a spec changes.
- OpenAPI / REST authoring: **no subagent** — load `api-design-skill` when editing a spec file (`openapi.yaml`/`openapi.json`/`swagger.yaml`) or code that generates one (FastAPI routes + Pydantic I/O, NestJS `@Api*`/`nestjs/swagger`, tsoa, `@asteasolutions/zod-to-openapi`, Spring + springdoc-openapi, Django DRF + drf-spectacular/drf-yasg). Apply its §Authoring Quality Gate (description + example on every operation/schema; `redocly lint` before done) at write time.
- Ticket / issue creation (GitHub or JIRA): **no subagent** — load `ticket-plan-workflow-skill` directly when trigger phrases appear ("create issue", "new issue", "jira ticket", "open issue", "bug report", "feature request", "log a ticket", "track this", "create plan", "ticket with plan").
- Image / screenshot / PDF / non-text content: the primary session is **text-only** and will hallucinate visual detail — always delegate analysis to `image-analyzer-subagent` (native multimodal, runs on `zai/glm-5v-turbo` vision tier — sees images directly, no external vision API; requires Z.AI auth / `ZAI_API_KEY`).

## Project-Scoped Install (`opencode-init`)

When the user wants to apply a **curated subset** of agents/skills to the **current project** (project-scoped, not global), use the `opencode-init` CLI (symlinked onto PATH by `setup.sh`). Trigger phrases: "install subagents here", "set up agents for this repo", "add review agents", "apply agents to this project", "project-level opencode config".

**Introspect before installing** (the LLM path — flags, not arrow keys):
1. `opencode-init --list categories` — see the groupings + counts.
2. `opencode-init --list agents --category review` — narrow to a category.
3. `opencode-init --describe code-review-subagent` — see what one agent requires (skills + delegates + model availability).
4. `opencode-init --expand review` — see the FULL resolved set a preset would install (incl. auto-pulled transitive deps).

**Install** (prefer presets; fall back to `--agents` for specifics):
```
opencode-init --project . --preset review --yes            # preset (recommended)
opencode-init --project . --agents code-review-subagent --yes   # specific agents (deps auto-pulled)
opencode-init --project . --preset review --dry-run        # preview, write nothing
opencode-init --project . --preset docs --yes --prune      # switch preset, remove the old subset
```
`--yes` = non-interactive (auto-resolve all skill + transitive-subagent deps). Without `--yes` in a real TTY it walks an interactive menu.

**Clean-slate caveat (IMPORTANT):** opencode **merges** config and **unions** agents/skills across `~/.config/opencode` and `<project>/.opencode`. A project subset only yields an *isolated* curated experience on a **clean slate** (no global deploy). If `~/.config/opencode/agents/` is non-empty, the project install is **additive** — the CLI detects this and warns. `permission.task` (scoped subagent-spawn allowlist) still restricts auto-spawning even with a global deploy, but a user can always `@`-mention any visible subagent directly. Recommend presets to the user; use `--describe`/`--expand` so they know what a choice pulls in before committing.

## MCP Tool Routing

- **Web fetch:** use built-in `webfetch` first; fall back to `zai-web-reader` only on failure (>5MB, timeout, encoding).
- **Local files:** always use built-in `Read` for local/`file://` paths. Never use MCP resource tools (`read_mcp_resource`, `list_mcp_resources`, `list_mcp_resource_templates`) for local files — those are for MCP server resources (DB schemas, APIs) only. Do not configure the `filesystem` MCP server; it is redundant with `Read`/`glob`/`grep` and causes tool-selection ambiguity.
- **Document → Markdown extraction:** when an agent encounters a `.docx`/`.pptx`/`.xlsx`/born-digital `.pdf` and needs text, route via the 4-tier rule in repo-root `AGENTS.md` → **Office Document Extraction Routing** (markitdown → docling → image-analyzer → pdf-specialist). Load `markitdown-mcp-skill` for the markitdown-specific decision tree; escalate to docling (`docling-mcp-skill` — CLI-on-demand or `--enable-pack docling`) when markitdown output is insufficient. The markitdown launcher is local-only; privacy details live in the skill + launcher README.

## Built-in Tool Preferences

- **Content search:** prefer `rg` (ripgrep) over `grep` when available — faster, respects `.gitignore` by default, multithreaded. Agents already fall back to `grep` automatically if `rg` is absent (no hard dependency). Install: `apt install ripgrep` / `brew install ripgrep` / `pacman -S ripgrep`.

## CodeGraph

CodeGraph is a **tools-only** MCP server (no resources). **The `codegraph_*` tools ARE the codegraph interface** — always start a code lookup with `codegraph_status`, then `codegraph_explore` / `codegraph_search` / `codegraph_files`. There is no `codegraph://` resource, so `read_mcp_resource` is the wrong tool and will error (do not call it). MCP resource reads are runtime-denied via `permission.read: { "*": "allow", "mcp:*": "deny" }` in opencode.json — opencode maps the MCP-resource tools to the `read` permission internally, so tool-name keys like `read_mcp_resource: deny` are silently ignored. **Due to an upstream opencode visibility bug (`session/tools.ts`), `read_mcp_resource` and `list_mcp_resources` remain in the model's tool list even though they are runtime-denied — do NOT attempt to call them; they will waste a step and return `DeniedError`.** Use `codegraph_*` tools or built-in `Read`/`glob`/`grep` instead.

**Main session — lightweight lookups only:** `codegraph_search`, `codegraph_callers`/`callees`, `codegraph_impact`, `codegraph_node`, `codegraph_files`, `codegraph_status`.
**NEVER call `codegraph_explore` or `codegraph_context` in the main session** — they flood the context. Spawn an explore agent for exploration.

**Pre-flight initialization:** before spawning any subagent that benefits from CodeGraph, check for `.codegraph/` in the project root. If absent, run `codegraph init -i`, wait for completion, then spawn. If init fails (not installed, non-code project, very large monorepo, read-only mount), proceed without CodeGraph — subagents fall back to grep/glob automatically. In CI/non-interactive contexts (no TTY, read-only mount), skip silently; never block the flow. If the user says "skip codegraph", write `.opencode/codegraph-skipped` to stop re-attempting init.

## Branch Workflow Setup Signal

When a subagent returns `NEEDS_GIT_BRANCH_SETUP: true`, the primary agent handles it — hub-and-spoke (setup subagents only *signal*; they do NOT load the skill or spawn `repo-ops-specialist-subagent` themselves):

1. Load `git-branch-workflow-setup-skill`.
2. Run its §Detection Logic (check for existing release tooling + skip markers).
3. If detection triggers: prompt the user per its §Question Tool Spec, or apply §Non-Interactive Fallback → Skip in headless/CI.
4. If the user accepts: delegate execution to `repo-ops-specialist-subagent` via the Task tool, passing the typed payload from §Delegation Spec.
5. If skipped: write `.opencode/branch-workflow-skipped`.

## Subagent Chaining

Subagents may spawn other subagents via the Task tool, gated by `permission.task` frontmatter. Hub-and-spoke (primary → subagent) is the preferred pattern.

## Verification & Quality Gates

**LSP is ambient, CLI is the gate.** LSP diagnostics (when a project's `opencode.json` enables them) give real-time type errors during edits — useful but not sufficient. Before declaring any non-trivial task done, run the project's explicit CLI checks; they're the source of truth.

- **Discover commands first:** check `package.json` scripts, `pyproject.toml` (`[tool.*]`), `Makefile`, or README. If unknown, ask the user; then record them in the project's `AGENTS.md` / `instructions` so they're not re-discovered.
- **Lint + typecheck** on every non-trivial change (fast feedback; catches what LSP misses project-wide).
- **Tests** when the change touches logic or a tested path.
- **Build** when the change touches build config, deps, or entry points.
- **If a gate fails, fix it** — don't report success with a known-broken gate. If it was already broken before your change, say so explicitly rather than silently inheriting it.

## Proactive LSP Recommendation (review agents)

When doing a review (code-review / architecture-review / language reviewers / pr-workflow) and **all three** hold:
- change set is large or cross-file (>10 files, or touches shared/imported modules), AND
- project `opencode.json` has no `lsp` key (`jq '.lsp // empty' opencode.json` is empty), AND
- a built-in LSP server matches the project's language,

…append a one-line **LSP recommendation** to the report's Recommended Actions: suggest enabling LSP with a ready-to-paste snippet. Framework→server mapping: TS/JS/Next.js/monorepo → `typescript`+`eslint`; Python → `pyright`; others per the [built-in LSP table](https://opencode.ai/docs/lsp/#built-in). Full snippets live in `nextjs-standard-setup-skill` / `python-backend-skill` / `monorepo-management-skill`. **Recommend only — never auto-edit `opencode.json`.** Rationale: LSP gives ambient cross-file type diagnostics during edits; CLI gates (lint/test/build) remain the source of truth.

## Skill Permission Allowlist

`opencode_app/opencode.json` uses a **global allowlist** for skills: `"permission.skill": { "*": "deny", "<skill>": "allow", … }`. Only explicitly-allowed skills appear in the primary session's `<available_skills>` listing; the rest are hidden (subagent-only, loaded via per-agent `permission.skill` overrides). This keeps the primary session's initial context lean.

**Skill profiles (deploy-time):** the shipped allowlist is the **full** profile. `./deploy/setup.sh --skill-profile lean|full` (default **lean**) rewrites ONLY the deployed copy's `permission.skill` block — lean = 29 primary-visible skills + `"*": "deny"`; full = shipped allowlist verbatim. Profiles live in `deploy/skill-profiles.json`; `deploy/apply-skill-profile.mjs` applies them (typo-guarded, fail-closed). Never hand-edit deployed copies — re-run setup.sh.

**Adding a new skill:** if the **primary** should see it, add `"<skill-name>": "allow"` to the `permission.skill` block in `opencode_app/opencode.json` — and, if it should be primary-visible under lean too, add it to `deploy/skill-profiles.json`'s `lean` array. If only a **subagent** needs it, add the allow to that subagent's frontmatter `permission.skill` block instead — the global deny won't affect self-scoped subagents, under either profile. New skills default to **hidden** until explicitly allowed.

**Subagent self-scoping:** Most subagents have their own `permission.skill` blocks — they are unaffected by the global allowlist and by the deployed profile. Only the primary + unscooped subagents (explorer, image-analyzer) inherit the deployed allowlist. See [Skills §Override per agent](https://opencode.ai/docs/skills/#override-per-agent).

## Commit Conventions

- Follow [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): description`.
- Atomic commits — one logical change each; split migration/ORM model/schema/logic/tests into separate commits.
- Wrap commit body at 72 chars (project commitlint may override, e.g. 120).
- Never mix style/formatting changes with logic changes in one commit.
- For granularity guidance, load `git-semantic-commits-skill`.

## Memory Hygiene

Proactive recall + capture via the `memory` tool (provided by the `opencode-superlocalmemory` plugin). Soft convention — fires only when an agent acts on it; for the full capture procedure (instinct model, confidence scoring, LEARNINGS/ markdown), load `continuous-learning-skill`.

**Recall (mode: `search`):** before any review, plan, or debug task, query `scope: project` with the task topic, `limit: 5`. Surface relevant learnings before acting; if empty, proceed silently.

**`LEARNINGS/*.md` manifest (auto-injected):** the `learnings-autoinject` plugin surfaces a compact titles+paths manifest of a project's `LEARNINGS/` markdown into the system prompt each session (on by default; `/learnings-off` to disable). No need to `glob` for discovery — the manifest tells you what exists; `read()` specific files on demand. Manual `glob`+`read` is now a fallback for fresh files added mid-session (use `/learnings-refresh`).

**Capture (mode: `add`):** after resolving a non-trivial error or making an architectural decision, store a 2-line summary with `type: error-solution` / `architecture` / `learned-pattern`. **One add per decision** — never log routine commits.

**Scope:** `scope: project` for repo-scoped learnings; `scope: user` for cross-project preferences only.

**Never** store secrets, PII, or file contents verbatim.

## Secret Hygiene (vibeguard advisory layer)

Vibeguard is the **hard control**: it masks secrets in provider-bound traffic (LLM requests) via regex patterns and restores real values at tool-execution time. These rules are an **advisory layer** — they reduce the likelihood of secret echo but can be defeated by prompt injection, model non-compliance (esp. `fast`-tier subagents), or context-window compaction. State this honestly: the only hard controls are (1) vibeguard regex masking and (2) `permission.read` deny for the `read` tool (primary agent only — subagents override with `{"*":"allow"}`).

1. **Never echo `.env` values in reply text.** Reference by `$VAR` name only. If you must reference a masked value inline, copy the exact `__VG_…__` placeholder verbatim — never truncate, reformat, or partially copy it (broken placeholders fail to restore at exec).
2. **Subagents report key NAMES, not values,** back to the primary. The vibeguard placeholder→value map is per-sessionID; a placeholder from the parent is an opaque string to a subagent and cannot be restored cross-session.
3. **Prefer `$VAR` env references** over inlining literals in generated scripts, configs, and commands.
4. **Vibeguard masks provider-bound traffic** and restores real values at tool-execution. Your job is to prefer `$VAR` and avoid unnecessary `.env` reads — not to act as a substitute filter.
5. **Never store secrets in the `memory` tool, LEARNINGS, or commit messages** (extends the Memory Hygiene rule above).
6. **Never use `/share` on sessions that processed `.env` secrets** — `/share` exports plaintext tool I/O; vibeguard has no `/share` hook.
7. **Fail-closed caveat:** if vibeguard is no-op (config missing, malformed, or `enabled:false`), bash/grep/MCP paths are fully unprotected. Treat any `.env` value as exposed and avoid processing it. Verify masking is active: `OPENCODE_VIBEGUARD_DEBUG=1 opencode` should show replace-counts > 0.
8. **Per-project overlay:** to add literal `keywords` (exact-match secrets vibeguard's regex misses), create an **uncommitted** `./vibeguard.config.json` at the project root. Note: the first config found wins (no merge) — a per-project config **completely overrides** the global one, so re-include the regex patterns if you need both.

For verification steps, per-project keyword setup, `$VAR` usage patterns, and fallback when vibeguard is disabled, load `security-audit-skill`.
